# 要件定義書 — mindmap_drive

作成日: 2026-08-28(最終更新: 2026-08-28)
ステータス: v1 ドラフト

## 1. 背景・目的

日々のアイデア整理・タスク分解・思考の構造化のために、自分専用のマインドマップ(アウトライン型)ツールが欲しい。既存の類似サービス(Workflowy, Notion 等)はあるが、自分の用途に最適化した軽量なツールを自作し、データの保存先を自分のGoogle Driveにすることで、特定のサービス・機器に縛られずどこからでも同じデータにアクセスできるようにしたい。

## 2. 想定ユーザー・利用シーン

- ユーザーは本人のみ。他者との共有・共同編集は現時点で想定しない
- 利用環境: PCブラウザ(Chrome想定)、スマホブラウザ(外出先での閲覧・簡易編集)
- 利用シーン例:
  - 思いついたアイデアをスマホでさっと箇条書きメモ
  - PCでじっくり構造を整理(階層の入れ替え、まとめ直し)
  - 過去に作ったマップを別の端末から開いて参照・追記

## 3. スコープ

### v1に含む
- ノード&エッジによる視覚的なマインドマップ編集(階層構造の作成・編集。実装時に当初のアウトライン(箇条書き)表示から変更。4.3節末尾の注記参照)
- ドラッグ&ドロップによるノードの再親子付け(ノードを別のノードへドロップすると、その子になる)
- 単一マップ内でのノードCRUD・並び替え・折りたたみ
- 複数マップの管理(一覧・新規作成・名前変更・削除)
- Google Drive を使った認証・保存・読み込み・自動保存
- ノードへの画像添付(Drive上に別ファイルとして保存)
- PC/スマホ両対応のレスポンシブUI
- キーボードによる高速な入力・操作(直感的で打ちやすいショートカット)
- Undo(元に戻す)による誤操作からの復旧

### v1に含まない(将来検討)
- 複数人での共同編集・リアルタイム同期(複数端末での同時編集は考慮しない。単一ユーザーが1つの端末で使う前提)
- オフライン編集(ネットワーク切断時の編集・後からの同期)
- ノードの自由配置(座標の手動指定・保存)。ノードの位置は木構造から自動レイアウトで算出し、ドメイン層には保存しない(4.3節末尾の注記参照)
- 画像以外のリッチテキスト装飾・添付ファイル(太字/リンク等の高度な書式)
- 全文検索、タグ付け
- Google Drive以外のストレージ(Dropbox等)への対応

## 4. 機能要件

### 4.1 マップ管理
- マップの新規作成(名前を付けて作成)
- マップ一覧表示(Google Drive上の対象ファイルを一覧化)
- マップを開く(選択したマップを読み込んで編集画面へ)
- マップ名の変更
- マップの削除

### 4.2 アウトライン編集
- ノードの追加(現在行の下に兄弟ノードを追加 等)
- ノードのインデント/アウトデント(階層の変更)
- ノードの並び替え(同一階層内での上下移動)
- ノードの折りたたみ/展開(子ノードの表示・非表示)
- ノードの削除: 子ノードを含めて削除する(カスケード削除)。確認ダイアログなしで即時削除し、入力を止めない速さを優先する(Undoで復旧可能なため、確認ダイアログは設けない)
- ノードのテキスト編集(プレーンテキスト。装飾は最小限)
- Undo(元に戻す): 直前の操作(削除・追加・編集・移動等)を取り消せる。ショートカットは `Ctrl+Z`

### 4.3 キーボード操作
- 「キーボードだけで思考のスピードを止めずに記録できる」ことを最優先の体験目標とする
- キーバインドは [MindMup](https://www.mindmup.com/help/guides/keyboard/) のショートカット体系を参考にする(ユーザーが直感に近いと評価したため)。v1のスコープ(アウトライン編集・画像添付)に合わせて以下を採用案とする:

| 操作 | ショートカット | 備考 |
|---|---|---|
| 兄弟ノード追加 | `Enter` | 編集中テキストの確定を兼ねる |
| 子ノード追加 | `Tab` | 選択ノードの子として新規ノードを追加 |
| アウトデント(親を挿入/階層を上げる) | `Shift+Tab` | |
| ノード削除 | `Backspace` / `Delete` | カスケード削除(4.2節)。確認なしで即時実行 |
| ノードの並び替え(同階層内で上下移動) | `Ctrl+↑` / `Ctrl+↓` | |
| ノード間移動(選択の移動) | `↑` `↓` `←` `→` | 兄弟・親子間の移動 |
| 折りたたみ/展開 | `/` または `F` | |
| 画像添付 | `I` | 4.6節の画像添付に割当 |
| 元に戻す(Undo) | `Ctrl+Z` | 直前の操作を取り消す |
| やり直し(Redo) | `Ctrl+Y` / `Ctrl+Shift+Z` | |
| ルートに戻る/表示リセット | `Esc` | |

- **実装時の調整(プレゼンテーション層実装時、およびキャンバス表示化後のユーザーフィードバックにより確定)**: 上表から以下のとおり変更した(`src/presentation/pages/MapEditorPage.tsx`冒頭のコメント参照)。キャンバス化に伴い、ノードに「選択(selected)」と「文字入力(editing)」の2モードを導入した
  - ノードをクリックすると選択状態になる(テキストは地の文表示のまま)。選択中の`Enter`は文字入力中と同じく常に新規の兄弟ノードを追加し、即座にその文字入力モードに入る。既存ノードのテキストを後から編集したい場合はダブルクリックで文字入力モードに入る
  - 子ノード追加は選択中・文字入力中どちらも`Tab`で直接作成する。「インデント」動作としては実装しない(再親子付けはドラッグ&ドロップのみで行う)。そのためアウトデント用のショートカットは無い(マウスのドラッグ&ドロップで行う)
  - ノード削除(`Backspace`/`Delete`)は、選択中はテキストの有無によらず即削除。文字入力中は従来通りテキストが空の時のみノード自体を削除する
  - 折りたたみ/展開は`/`/`F`単独だと入力中の文字と衝突するため、選択中のみ`Ctrl+←`(折りたたみ)/`Ctrl+→`(展開)に変更(文字入力中はテキストカーソルの単語移動と衝突するため割り当てない)
  - 画像添付は`I`単独だと入力中の文字と衝突するため`Ctrl+I`に変更。加えて、ノードへ画像ファイルを直接ドラッグ&ドロップして添付することもできる
  - ノード間移動の`↑`/`↓`は同じ親を持つ前後の兄弟ノードへ移動する(子孫へは移動しない。当初DFS順で実装したが、子ノードへ入り込んでしまい直感に反するとのユーザーフィードバックにより兄弟間のみに変更)。`←`/`→`は選択中のみ親ノード/最初の子ノードへの移動に割り当てる(折りたたまれている場合や子が無い場合、`→`は何もしない)。文字入力中は標準のテキストカーソル左右移動を優先し、ノード間移動には割り当てない
  - `Esc`は、文字入力中に押すとノードは選択されたまま文字入力モードのみを抜ける動作とした(v1にズーム機能がないため「ルートに戻る/表示リセット」とはしない)
  - 文字入力中の`Shift+Enter`でカーソル位置のテキストを分割し、後半を新しい兄弟ノードにできる(`MindMap.splitNode`。ユーザーフィードバックにより追加)
  - `Ctrl+クリック`/`Shift+クリック`で同じ親を持つ兄弟ノードを複数選択できる(異なる親のノード同士は選択不可)。複数選択中の`Enter`で、選択したノードを兄弟内の並び順で1つに統合する(`MindMap.mergeNodes`。テキストは改行連結、子ノード・添付画像は先頭ノードへ集約。`Esc`で複数選択を解除。ユーザーフィードバックにより追加)
  - `Ctrl+Shift+9`でマップ内の全ノードを展開、`Ctrl+Shift+0`で全折りたたみする(`MindMap.expandAll`/`collapseAll`。全展開はブラウザの検索(Ctrl+F)で全文検索できるようにする用途を想定。特定ノードへの操作ではないため、フォーカス位置によらず常に効く。`Ctrl+9`/`Ctrl+0`はブラウザ標準の予約済みショートカット(タブ切り替え/ズームリセット)と衝突するため採用しなかった。ユーザーフィードバックにより追加)

- **表示方式の変更(プレゼンテーション層実装完了後、ユーザーからの追加要望で決定)**: 当初はWorkflowyライクな箇条書き(アウトライン)表示のみを想定していたが、「ノードとエッジを視覚的に表示し、ドラッグ&ドロップで自由に移動・再親子付けしたい」という要望を受け、ノード&エッジのキャンバス表示(React Flow採用)に変更した。ノードの位置は木構造から自動レイアウトで算出する方式(3節参照)とし、ドメイン層(親子ツリー構造)自体には変更を加えていない。キーボードによる高速入力(本節)は、この新しい表示方式の上でも維持している(ノード=画面上の箱、テキスト入力欄はそのまま)

- 詳細な確定・微調整(競合するキーの調整、モバイルでの代替操作等)はUI設計フェーズで行う

### 4.4 Google Drive連携
- Googleアカウントでの認証(OAuth 2.0)
- 認可スコープは自アプリが作成したファイルのみアクセス可能な最小権限(`drive.file` 相当)を基本方針とする
- 1マップ = 1 JSONファイル としてDrive上に保存
- 自動保存: 編集操作のたびに(または短い間隔で)自動的にDriveへ保存する。手動保存ボタンは必須としない
- マップの読み込み、一覧取得

### 4.5 レスポンシブ対応
- PCではキーボード操作を中心とした編集体験
- スマホではタッチ操作(タップでノード選択、スワイプやボタンでインデント操作等)を考慮したUI

### 4.6 画像添付
- ノードに画像を1枚以上添付できる(用途: スクリーンショットや参考画像の貼り付け)
- 添付方法は`Ctrl+I`(ファイル選択)、ノードへの画像ファイルの直接ドラッグ&ドロップ、および`Ctrl+V`でのクリップボード画像貼り付け(Webページ等からコピーした画像を想定。実装はユーザーフィードバックにより追加)の3通り
- 画像はマップ本体のJSONとは別に、アプリ専用フォルダ配下の`images/<mapId>/`というマップごとのサブフォルダに個別ファイルとして保存する(当初は同じアプリフォルダ直下に平置きしていたが、無秩序に増えて見づらいというユーザーフィードバックによりサブフォルダ化した)
- ノードのJSONには添付画像のDriveファイルID(参照)のみを保持する
- 画像はノード上に直接サムネイル表示する。キャンバスの自動レイアウトは、添付画像を持つノードがサムネイル分縦に大きくなることを見積もって間隔を広げ、隣接ノードと重なり合わないようにしている(`canvasLayout.ts`の`separation`。ノードの実測サイズではなく概算のため、添付枚数が多いノードでは完全には防げない場合がある)

## 5. 非機能要件

- **機器非依存**: ローカルストレージのみにデータを閉じ込めない。Google Driveを正とし、どの端末からアクセスしても同じデータが見られること
- **入力の速さを最優先**: キー入力から画面反映までの体感遅延を最小化する。自動保存やDrive通信によってタイピングがブロックされないこと(保存は非同期・裏側で行う)
- **オンライン前提**: v1はネットワーク接続がある状態での利用を前提とする。オフライン対応は将来課題とする
- **単一端末利用前提**: 同時に複数端末から同じマップを編集することは想定しない。競合解決の仕組みは持たず、後勝ち(最後の自動保存が正)でよいものとする
- **想定データ規模**: 1マップあたり数百〜数千ノード程度を想定(個人利用のため大規模データは想定しない)
- **セキュリティ**: 自分のGoogleアカウントでの認証のみ。Driveアクセスは最小権限スコープに限定し、アプリが作成・所有するファイル以外にはアクセスしない
- **対応ブラウザ**: 最新版のChromeを主対象とし、Safari(iOS含む)でも動作することを目標とする
- **パフォーマンス**: 数千ノード規模でも編集操作(追加・折りたたみ等)がストレスなく行えること

## 6. 制約条件

- フロントエンドオンリー構成(専用バックエンドサーバーは持たない)。静的ホスティングで完結させる
- React + TypeScript を使用
- DDD(ドメイン駆動設計)の考え方でドメイン層を設計し、Google Drive等の外部依存から分離する
- 個人開発のため、開発・運用コストは最小限に抑える(有料インフラは基本利用しない)

## 7. 用語集(ユビキタス言語の種)

| 用語 | 定義 |
|---|---|
| マップ(Mind Map) | 1つのアウトライン全体。Google Drive上の1つのJSONファイルに対応する |
| ノード(Node) | マップを構成する個々の項目。テキストと子ノードのリストを持つ |
| 階層(Hierarchy / Depth) | ノードの親子関係によって決まる深さ |
| 折りたたみ(Collapse) | 子ノードを一時的に非表示にする表示状態(データ自体は保持) |
| インデント/アウトデント | ノードの階層を1段深く/浅くする操作 |
| 画像添付(Attachment) | ノードに紐づく画像。Drive上に別ファイルとして保存され、ノードはその参照(ファイルID)を持つ |

※ ドメインモデリングのフェーズでエンティティ・値オブジェクトとして正式に定義し直す。

## 8. 未決事項・リスク

- OAuthクライアントID・リダイレクトURI設計(フロントエンドオンリー構成向けの認可コードフロー+PKCEを想定。詳細はアーキテクチャ設計フェーズで確定)
- 自動保存の粒度・頻度(1操作ごとに保存するか、一定間隔でまとめて保存するか。Drive APIのリクエスト数・レート制限とのバランスを設計時に検討)
- 画像の最大サイズ・対応フォーマット(スクリーンショット用途を想定。上限サイズや圧縮の要否をUI/アーキテクチャ設計時に検討)
- 1ノードに添付できる画像の枚数上限(現状は「1枚以上」とだけ規定。上限の要否は設計時に検討)
- Undo履歴の範囲(何操作分・何分間保持するか、ページ再読み込み後も復元可能にするか)と自動保存タイミングの関係(Undoで戻した状態を誤って自動保存で上書きしないための整合設計)
